# Trading Safety Rules

These rules apply to every change that touches orders, accounts, credentials, wallets, or external APIs.

1. **Paper only.** The system never places real orders and never moves funds. The matcher fills paper orders against live public market data or replayed fixtures. Market data access is limited to the public, unauthenticated market-data endpoints of Coinbase and Backpack (`wss://ws.backpack.exchange`, `https://api.backpack.exchange` public market routes). Never call an authenticated Coinbase or Backpack endpoint, never add API keys, API secrets, or request signing for either venue, and never add trading, order, deposit, or withdrawal endpoints. No testnet trading either.
2. **One order path.** Every new order, from the web UI, the TUI, the LLM parser, or the MCP server, goes through `server/src/router.ts`, which calls the Risk_Engine before sending any command to the engine. No other module may send `PlaceOrder`, `Cancel`, `CancelAll`, or `ResetAccount` to the engine.
3. **Confirm before placing.** Command bar and plain-English orders produce an Order_Preview. The router accepts them only after the same client confirms that preview, on the same account.
4. **The LLM never trades.** LLM output is untrusted input: validate it with Zod, turn it into command text, and parse it with the normal Command_Parser. It can only produce a preview.
5. **Risk limits are not optional.** Do not add bypass flags. The kill switch (`KILL_SWITCH=true`) rejects every new order, on every account.
6. **Secrets.** Secrets (`OPENAI_API_KEY`, `DATABASE_URL`, `DIRECT_URL`, `SESSION_SECRET`, and the MCP's `TERMINAL_TOKEN`) come only from environment variables. Treat the whole `DATABASE_URL` and the whole `DIRECT_URL` as secret, not just their passwords. Session_Tokens and TUI Pairing_Secrets are secrets too. Never log any of them, return them in responses (except the one response that issues a Session_Token), write them to files (except the gitignored `.env` and the TUI's own 0600 token file), or commit them. Locally they live in `.env` (gitignored). Deploy secrets are set in the Render dashboard (`sync: false`), except `SESSION_SECRET`, which Render generates (`generateValue: true`).
7. **Untrusted input.** Validate WebSocket messages, REST parameters, auth request bodies, SIWS messages, MCP tool arguments, fixture names (`^[a-z0-9-]+\.jsonl$`, no paths), venue market-data messages, and engine output at the boundary. Database access only through the Prisma Client API or `$queryRaw`/`$executeRaw` tagged templates. Never `$queryRawUnsafe` or `$executeRawUnsafe`, and never build SQL by string concatenation.
8. **Origins.** Browser WebSocket connections, `/auth/nonce`, and `/auth/verify` are accepted only from `ALLOWED_ORIGINS`. The SIWS domain and URI must match that origin.
9. **Wallets sign the sign-in message only.** A wallet is asked to sign exactly one thing: the SIWS sign-in message. Never request `signTransaction`, `signAllTransactions`, `signAndSendTransaction`, `signAndSendAllTransactions`, or any token approval or delegation, and never build a Solana transaction. The web UI uses only the `standard:connect`, `standard:disconnect`, `solana:signIn`, and `solana:signMessage` features. The server never contacts a Solana RPC endpoint; `solana:mainnet` in the SIWS message is an identity claim only.
10. **Accounts come from the verified session.** The `account_id` on every order Command is set by the server from the verified session of the requesting connection (or REST Bearer token), and is `guest` without one. Never take an account id, wallet address, or similar field from client input, MCP arguments, or LLM output. The only client-supplied address the server trusts is the one inside a SIWS message whose Ed25519 signature it has verified. Account events go only to connections on that account (`account:<account_id>` topic). One account can never cancel, reset, or see another account's orders.
