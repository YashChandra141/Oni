# Trading Safety Rules

These rules apply to every change that touches orders, accounts, credentials, wallets, or external APIs.

1. **Paper only.** The system never places real orders and never moves funds. The matcher fills paper orders against live public market data or replayed fixtures. Market data access is read-only and limited to the Endpoint_Allowlist in `server/src/net/http.ts` (the allowlisted HTTP wrapper, with its Rust twin in the engine's `feed/allowlist.rs`): the public, unauthenticated market-data endpoints of Coinbase and Backpack (`wss://ws.backpack.exchange`, `https://api.backpack.exchange` public market routes), `GET https://api.jup.ag/price/v3`, and `GET https://api-v3.raydium.io/mint/price` and `/pools/info/mint`. Never call an authenticated Coinbase, Backpack, or Raydium endpoint, never add API keys, API secrets, or request signing for Coinbase, Backpack, or Raydium, and never add trading, order, deposit, or withdrawal endpoints. Binance and Bybit are not used. The one exception is the optional `JUPITER_API_KEY`: it may be sent as the `x-api-key` header to the Jupiter Price API only, because it raises a data rate limit and authorizes no trading. Never call a Jupiter swap, order, or execute endpoint, and never call any Raydium transaction host (`transaction-v1.raydium.io`) or any `/transaction` path, ever. A response that carries a transaction field is discarded. News and LLM provider hosts are non-trading services that only the Server may call, through the same allowlisted HTTP wrapper. No testnet trading either.
2. **One order path.** Every new order, from the web UI, the TUI, the LLM parser, the AI analyst, or the MCP server, goes through `server/src/router.ts`, which calls the Risk_Engine before sending any command to the engine. No other module may send `PlaceOrder`, `Cancel`, `CancelAll`, or `ResetAccount` to the engine. TWAP child orders are sent only by the Router, each through the Risk_Engine at its scheduled time. The AI analyst, the news code, and the DEX adapters never send order Commands.
3. **Confirm before placing.** Command bar, plain-English, and AI analyst orders produce an Order_Preview. The router accepts them only after the same client confirms that preview, on the same account. A confirmed TWAP Order_Preview authorizes the child orders in its TWAP_Plan and nothing else. The Router cancels the remaining child orders on disconnect, account change, engine restart, a rejected child, or user cancel.
4. **The LLM never trades.** LLM output is untrusted input: validate it with Zod, turn it into command text, and parse it with the normal Command_Parser. It can only produce a preview. This covers every provider (OpenAI, Anthropic, NVIDIA NIM, Ollama), the plain-English parser, the AI analyst, and every Copilot action. News headlines and all other external text in a prompt are untrusted data, delimited from the instructions, and never executed.
5. **Risk limits are not optional.** Do not add bypass flags. The kill switch (`KILL_SWITCH=true`) rejects every new order, on every account. The rejection reasons are `kill_switch`, `rate_limit`, `max_open_orders`, `price_band`, `max_order_value`, `max_position`, `insufficient_balance`, `venue_unavailable`, `stale_market_data`, `price_deviation`, `engine_unavailable`, and `account_limit`; AI requests are limited with `ai_rate_limit` and `ai_daily_cap`. None of them has a bypass. An order that would leave an account's Free_Balance below zero is rejected with `insufficient_balance`, by the Risk_Engine and again by the engine.
6. **Secrets.** Secrets (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `NVIDIA_API_KEY`, `NEWS_API_KEY`, `CRYPTOPANIC_API_KEY`, `JUPITER_API_KEY`, `SESSION_SECRET`, and the MCP's `TERMINAL_TOKEN`) come only from environment variables. Treat `OLLAMA_BASE_URL` and `NVIDIA_BASE_URL` as secrets too, because a URL can carry credentials: the Server rejects a URL with embedded credentials and logs only its host. Session_Tokens and TUI Pairing_Secrets are secrets as well. Never log any of them, return them in responses (except the one response that issues a Session_Token), write them to files (except the gitignored `.env` and the TUI's own 0600 token file), or commit them. `CRYPTOPANIC_PLAN`, `NEWS_PROVIDER`, `NEWS_TTL_SECONDS`, `NEWS_ALLOW_NEWSAPI_IN_PRODUCTION`, `STARTING_BALANCE`, `BALANCE_SLIPPAGE_BPS`, `DEX_*`, `AI_RATE_PER_MIN`, and `AI_DAILY_CAP` are non-secret settings. Never log a full request URL for a news or exchange host, because the CryptoPanic `auth_token` travels in the query string. Never log the text of an LLM request or response. Locally the secrets live in `.env` (gitignored). Deploy secrets are set in the Render dashboard (`sync: false`), except `SESSION_SECRET`, which Render generates (`generateValue: true`). There is no database, so there are no database URLs.
7. **Untrusted input.** Validate WebSocket messages, REST parameters, auth request bodies, SIWS messages, MCP tool arguments, fixture names (`^[a-z0-9-]+\.jsonl$`, no paths), venue market-data messages, and engine output at the boundary. Validate LLM output, News_Provider responses, and Jupiter and Raydium responses with Zod at the boundary too. Token mint addresses come only from the committed Venue_Symbol_Map, never from client input, LLM output, or news data.
8. **Origins.** Browser WebSocket connections, `/auth/nonce`, and `/auth/verify` are accepted only from `ALLOWED_ORIGINS`. The SIWS domain and URI must match that origin.
9. **Wallets sign the sign-in message only.** A wallet is asked to sign exactly one thing: the SIWS sign-in message. Never request `signTransaction`, `signAllTransactions`, `signAndSendTransaction`, `signAndSendAllTransactions`, or any token approval or delegation, and never build a Solana transaction. The web UI uses only the `standard:connect`, `standard:disconnect`, `solana:signIn`, and `solana:signMessage` features. The server never contacts a Solana RPC endpoint; `solana:mainnet` in the SIWS message is an identity claim only.
10. **Accounts come from the verified session.** The `account_id` on every order Command is set by the server from the verified session of the requesting connection (or REST Bearer token), and is `guest` without one. Never take an account id, wallet address, or similar field from client input, MCP arguments, or LLM output. The `venue` of an order comes from the confirmed Order_Preview and is validated against the Venue identifiers; neither LLM output nor MCP arguments can set an account. The only client-supplied address the server trusts is the one inside a SIWS message whose Ed25519 signature it has verified. Account events go only to connections on that account (`account:<account_id>` topic). One account can never cancel, reset, or see another account's orders.
